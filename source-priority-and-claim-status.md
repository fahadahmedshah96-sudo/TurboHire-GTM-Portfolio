# Source priority, claim status, and public-use rules

## Source priority

For a specific deliverable, use this order and record the relevant source:

1. The user's latest explicit instruction for that asset, region, and audience.
2. Current approved product documentation, release notes, legal/security guidance, or product-owner confirmation for factual product claims.
3. Current approved public company material for public positioning, terminology, and published proof.
4. Current internal strategy or content briefs for intended positioning and planned messaging. These are not automatically evidence of live product availability.
5. Recent decks, reports, posts, newsletters, and website drafts, checked for date, audience, region, and approval status.
6. Older public pages, historical decks, archived copy, and model memory as discovery aids only.

When sources conflict, do not blend them. State the conflict, use the higher-priority source, and ask for confirmation only if the deliverable depends on an unresolved product or approval decision.

## Claim-status labels

Use these labels in research notes and agent outputs:

- **Approved baseline** — current source supports the wording for this audience and use.
- **Verified public** — visible in a current public TurboHire source; still check that it is live and unchanged before quoting.
- **Internal direction** — strategy or draft guidance; not proof of a live capability or public approval.
- **Region-specific** — valid only for the named geography, market, or configuration.
- **Maturity-limited** — beta, pilot, planned, release-soon, or under development.
- **Dated** — time-bound data or claims that need a date and freshness check.
- **Needs verification** — insufficient or conflicting evidence.
- **Do not publish** — confidential, customer-sensitive, unsupported, or not approved for external use.

## Evidence requirements

For statistics and performance claims, retain the exact source, publication date, geography, sample or denominator, metric definition, and any limitation. For customer claims, confirm the exact wording and permission to publish. For competitor claims, prefer dated primary sources and attribute vendor-reported figures as vendor claims.

For product capabilities, capture region, configuration or integration prerequisites, maturity, and the latest verification date. For external research, distinguish the source's findings from TurboHire's interpretation.

## Public GitHub portfolio rules

- Include only information already public or explicitly approved for public use.
- Do not upload internal strategy spreadsheets, confidential battlecards, call notes, unpublished customer information, private product screenshots, or internal performance metrics.
- Do not copy internal Drive documents into this repository. Link only to sources intended for public access.
- Prefer short, attributed summaries and public source links over reproducing full reports or copyrighted text.
- Clearly label hypothetical examples and calculator assumptions. Never imply they are customer outcomes.
- Do not add credentials, API keys, private URLs, or personal data to repository files or GitHub Actions logs.

## Known source-drift warning

Some older TurboHire pages and posts use “self-driving hiring,” “ATS,” or “orchestration” as the lead description. Treat such material as historical unless a current approved brief says otherwise. The current positioning baseline for this context library is **Frontline Hiring with Automation and AI**, with SuperAgent as the execution layer and humans accountable for hiring decisions.
